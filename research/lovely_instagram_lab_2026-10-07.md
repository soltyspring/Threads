# lovely Instagram 노출 탐색 실험

목표는 Threads 홈 조회수보다 Instagram 추천 유입을 확보하는 것이다. Instagram 추천을
강제하는 API나 보장된 포맷은 없다. 공개 계정의 다른 앱 추천 허용 설정도 직접 확인해야 한다.
사용자가 제공한 cute 사례는 Instagram 비중 85.69~98.87%였지만 lovely의 성과를 보장하지 않는다.
계정 규모와 이력이 달라 두 계정의 조회수 차이를 포맷의 인과 효과로 해석하지 않는다.

## 설계

- 30일 × 하루 24개 = 720개, lovely 전용 SQLite/JSON/cron. cute 큐는 변경하지 않는다.
- 매일 10개 비교 쌍: 300쌍/600개. 9개 단일 조건 비교(길이, 열 수, 기호 간격, 빈 줄,
  제목 유무, 제목 문구, 기호 순서, 들여쓰기, 줄 폭)와 1개 다변량 탐색(기호+표정 혼합).
- 길이는 8개/24개 원소, 열 수는 2열/4열, 폭은 추정 16셀/40셀을 비교한다.
  자동 줄바꿈 때문에 실제 열 수가 줄 수 있으며 실제 행 수·폭·문자 수를 별도로 기록한다.
- 하루 4개 비대조 탐색: 작은 장면, 대칭 배열, 컬러 이모지 혼합, 초압축형. 유형별 월 30개.
- 12개 주제를 매일 각 2회, 월 각 60회 배정한다. 조건/주제/시각은 분산한다.
- 비교 쌍의 게시 간격은 12시간, 날짜별 A선행/B선행을 교대로 배정한다.
  각 조건에 A선행 15일, B선행 15일을 확보한다. 자연 추천은 무작위 배정되지 않으므로
  시간대·누적 노출·주제·이전 글 간섭이 여전히 남는다. 인과 증명이 아닌 탐색 비교다.
- cute 예약과 서버 부하를 분산하도록 lovely는 매시 30분에 게시한다.
- 글자 크기는 Threads 텍스트 API에서 지정할 수 없다. 기호 밀도·폭·배치를 실험하며
  display_cells는 Unicode 기반 보수적 추정으로 실제 Instagram 카드 렌더링과 같지 않다.
- 실제 게시글에는 실험 라벨을 넣지 않는다. 조건과 첫 네 줄은 JSON 메타데이터에만 남긴다.

## 중복과 안전

lovely의 기존 게시글, cute 분석 DB와 기존/현재 예약 이력을 제외한다. 제목·공백·순서만
다른 재탕과 0.72 이상의 기호집합/5글자 조각 유사도를 검사한다. 단, 동일 비교 쌍의 A/B는
단일 조건을 분리하려고 같은 기호를 의도적으로 재사용한다. 따라서 720개 모두 텍스트는
다르지만 600개는 300개 원본 조합의 비교 변형이다. 모든 글이 완전히 다른 원본은 아니다.

LOVELY 토큰의 username을 매 게시 전에 확인한다. 계정별 DB와 export/cron lock을 분리한다.
게시 응답이 불명확하면 lovely 큐만 중단하며 자동 재시도하지 않는다. 적용 전 DB와 계획을
백업하고 교체 대상 pending은 삭제하지 않고 cancelled로 보존한다.

## 평가

1. 주요 지표: 게시 후 동일 경과시간(예: 24/72시간)의 Instagram 조회수 추정치와 유입 비중.
   비중만 높고 절대 조회수가 낮은 글은 성공으로 선정하지 않는다.
2. 보조 지표: 총조회수, 공유/리포스트, 반응률, 게시물별 팔로우. 별도의 목적함수로 유지한다.
3. API 수집은 총조회수·반응을 제공하며 현 수집기에는 Instagram 출처별 지표가 없다.
   공식 Meta Threads API 예제는 `views,likes,replies,reposts,quotes,shares`를 사용한다:
   https://www.postman.com/meta/threads/request/434u2bd/get-post-insights
   네이티브 인사이트의 총조회수와 Instagram %를 수동 입력하여 출처를 명시한다.
4. `instagram_views_estimate = total_views × instagram_percent / 100`. 화면의 반올림 값은
   `--approximate`를 붙여 정확한 API 수치로 오인하지 않도록 한다. 수집 시각도 저장한다.
5. 24/72시간 관측이 없는 글은 해당 비교에서 제외한다. 월별 누적 수치를 바로 비교하지 않는다.
   같은 계정·주제·조건의 반복 쌍 중앙값과 성공률을 보고, 바이럴 한 글만으로 승자를 정하지 않는다.

예시(실제 게시된 lovely post ID로 교체):

```bash
.venv/bin/python lovely_lab.py observe --post-id POST_ID --views 100000 --instagram-percent 98.24 --follows 3 --approximate
```

API 총지표는 매일 전용 `runtime/lovely_analytics.sqlite3`에 누적한다. 수동 출처별 관측은
`runtime/lovely_schedule.sqlite3`의 `instagram_observations`에 저장한다. 자동 승자 선정이나
진행 중 큐 재배치는 하지 않는다. 먼저 데이터를 모은 뒤 다음 캠페인을 조정한다.
